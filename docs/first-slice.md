# 다음 구현: 가상 사건 수신 → 저장 → 조회

이 문서는 제품 첫 기능의 작업 지시서입니다. DB 연결·초기 마이그레이션 시험을 마쳤고 정식 사건 검증·등록 조회·로컬 MQTT 연결 코드를 추가했습니다. 실제 실행 여부는 [현재 상태](status.md), 실행 절차는 [DB 준비](database.md)를 봅니다. 사용자 실습으로 정상→모순 거부→정상 수신을 확인했습니다. [검증 보완 기준](design/event-ingest-v1.md)의 추가 의미 검사도 구현·자동 테스트를 마쳤습니다. 정책 fixture·격리 저장소·revision 준비와 저장·ACK 구현 및 PostgreSQL 시험도 마쳤습니다. [새 저장 모드 실습](event-storage.md)에서 정상·중복·충돌·역순의 MQTT 응답과 SQL 결과까지 확인했습니다. M1의 정식 인증·조회까지 구현했습니다. [실행 안내](authenticated-read.md)를 보고, 다음으로 heartbeat·SSE를 연결합니다.

## 완료 모습

2026-11-14 후속 방향: 개별 학습 실습보다 공개 조회 데모 구현을 먼저 진행합니다. [M0 기반 작업](demo-foundation.md) 이후에는 임시 조회 인증 대신 정식 로그인·세션·CSRF·구역 권한을 조회 API와 함께 구현합니다. 아래 0~4단계는 저장 기능까지의 기존 작업 기록입니다.

PC 가상 장치가 사건 예제를 발행하면 서버가 저장하고 응용 ACK를 회신합니다. 조회 API에서 같은 사건과 현재 상태를 확인합니다. 같은 메시지를 다시 보내거나 오래된 메시지를 뒤늦게 보내도 데이터가 중복되거나 현재 상태가 되돌아가지 않습니다.

## 첫 입력과 출력

| 항목 | 기준 |
|---|---|
| 입력 | 기존 examples.json의 guidance_complete. 과거 사건 재생으로 사용 |
| 토픽 | parking/v2/devices/{device_id}/events, QoS 1, retain=false |
| 응용 ACK | 같은 장치 /acks, 원래 message_id 유지 |
| 조회 | GET /api/zones/{id}/status, 기존 ZoneView 전체 계약 |
| 선행 데이터 | 등록 장치·구역·정책. 원본 예제의 참조 대상과 일치하는 개발 fixture |

이력 재생만으로 현재 장치가 ONLINE이거나 실제 안내가 성공했다고 표시하지 않습니다. heartbeat의 연결 최신성·camera 관측 최신성은 별개입니다. 상태 조회에 필요한 초기값은 정식 계약에 맞는 미확인/빈 상태로 구성하고, 성공처럼 보이는 임의 값을 채우지 않습니다.

## 최소 인수 시험

- 정상 1건: DB 반영과 커밋 후 ACK, 조회의 ID·상태·revision 일치.
- 같은 ID·같은 내용: 두 번째는 DUPLICATE, 이력 중복 없음.
- 같은 ID·다른 내용: 격리 후 REJECTED, 현재 상태 훼손 없음.
- seq 12 → 10: 사건·snapshot 각각의 순서 조건 확인. 무조건 모든 과거 메시지를 버리지 않음.
- DB 저장 실패: 성공 ACK 없음. 동일 메시지 재전송 뒤 한 번만 저장.
- 커밋 뒤 ACK 유실: 재전송에 DUPLICATE, 현재 상태 유지.
- 조회: 기존 Schema·OpenAPI에 맞는 null·필드·타입. 한 시점의 읽기 보장.

위 결과는 **PC 가상 통합 시험**입니다. 실제 보드·AI 성능·물리 출력 시험은 아닙니다.

## 동시 수신·메시지 급증 검토 항목

2026-11-13 학습 중 제기한 질문을 후속 구현에 반영한다.

- 저장 기능 구현 시: 같은 message_id가 동시에 도착해도 DB 제약·트랜잭션으로 한 번만 반영한다. 동일 장치·구역의 오래된 상태가 최신 상태를 덮어쓰지 않도록 기존 순서 규칙을 적용한다. 도착 순서와 실제 사건 순서는 구분한다.
- 통합 기능 이후: 짧은 시간에 100/500건을 보내는 시험과 일정 속도로 지속 발행하는 시험을 분리한다. 건수뿐 아니라 메시지 크기·초당 발행량·지속시간·장치 수를 기록하고, 전송/수신/고유 저장 건수·지연·오류·자원 사용을 비교한다. 수치는 시험 입력 후보이며 처리 성능을 보장하는 값이 아니다.
- 병목 확인 후: 용량이 제한된 대기열과 작업 스레드 분리의 필요성을 판단한다. 대기열 포화 시 동작, 재전송·응용 ACK 시점, 장치·구역별 순서 보존을 먼저 정한다. 무제한 대기열이나 메시지마다 새 스레드를 만드는 방식으로 해결하지 않는다.

학습 프로필은 동기 수신 로그·QoS 0만 확인한다. 이 결과를 제품의 무손실·동시 저장·부하 처리 보장으로 해석하지 않는다.

## 이번에 구현하지 않는 것

M0 기반과 M1 정식 로그인·조회까지 구현했습니다. heartbeat·SSE와 웹 화면은 다음 단계입니다. 관리자 명령·사진 업로드·보드 SDK는 첫 공개 조회 데모와 별도로 진행합니다. API 접근 제한을 전역 해제하지 않습니다.
