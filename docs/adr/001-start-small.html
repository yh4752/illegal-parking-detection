빠르게 읽으려면 팀 요약과 웹 인계 계획을 보세요.

사건 수신·저장·ACK의 정상·중복·충돌·역순 처리를 MQTT/SQL로 확인했습니다. 로그인·조회 API와 heartbeat·실시간 화면을 작성했고, 인계 환경을 통합 시험 중입니다. 공개 배포와 외부 접속 검증은 별도입니다. 그림은 목표 구조이며 구현·시험의 실제 범위는 현재 상태에서 확인하세요.

ADR-001: 한 서버의 첫 기능부터 시작

  • 날짜: 2026-11-11
  • 상태: 이번 구현 골격에 채택. 제품 범위·시간·역할 계약 변경 없음.

배경

팀은 각자 작은 결과물을 만들어 보기로 했다. 백엔드는 보드 없이 MQTT 수신·저장·조회부터 시작한다. 전체 설계 v1.43은 있으나 실행 코드가 없으므로, 이해할 수 있는 구조와 실제 프로젝트 시작점이 필요하다.

결정

  1. 기존 Kotlin/Spring Boot 단일 애플리케이션을 유지한다. Gradle 멀티모듈·마이크로서비스를 추가하지 않는다.
  2. 기동 골격과 로컬 인프라 설정부터 만들고 첫 업무 기능은 별도 작업으로 수행한다. 빈 업무 클래스는 만들지 않는다.
  3. C4 L1/L2/L3는 목표 구조, 상태표는 실제 구현 범위를 설명한다. 코드 수준 클래스도는 필요할 때 작성한다.
  4. 초기에는 arc42 12항목을 짧게 채웠으나, 2026-11-11 검토 후 필요한 목표·경계·구성·흐름·결정·막힌 항목만 선택했다. 팀 본문은 다섯 질문과 C4 L2 한 장으로 정리하고 L3는 백엔드 문서로 분리한다. 원격 배포·공통 설계·품질 트리·용어집을 별도 장으로 새로 채우지 않는다.
  5. JDK 17, Spring Boot 3.5.16, Kotlin 2.1.21, Gradle 8.12.1을 개발 시작 버전으로 고정한다. Boot 3.5 요구 사항과 실제 의존성 해석 결과, Kotlin의 Gradle 호환 범위를 함께 확인한다. 기존 설계의 라이브러리 계열을 유지하며 최신 메이저로 바꾸는 작업을 이번 범위에 넣지 않는다.
  6. 로컬 DB·브로커는 루프백에만 노출한다. 평문·익명 MQTT 개발 설정과 운영 TLS·ACL 설정을 구분한다.

결과와 비용

보드 준비 전에 서버 개발을 진행할 수 있고, 가상 장치는 이후 재현 도구로 유지된다. 반면 골격 기동만으로 MQTT/DB 연동이 되지는 않는다. 첫 기능에서 의존성·마이그레이션·인증 개발 설정·실제 통합 시험을 추가해야 한다. 버전 고정이 보안·장기 지원을 보장하지 않으므로 배포 전 지원 상태와 패치를 검토한다.

재검토 조건

실제 모듈 경계가 반복적으로 충돌하거나, 독립 배포가 필요한 기능이 생기거나, 선택 버전의 지원·호환 문제가 확인되면 변경 ADR을 작성한다. 추측만으로 시스템을 분할하지 않는다.

첫 CI에서 확인한 버전 수정

2026-11-11 첫 CI 실행에서 Kotlin 1.9.25 컴파일러와 실제로 해석된 kotlin-reflect/stdlib 2.1.21의 메타데이터가 충돌했다. 컴파일러를 2.1.21로 맞추고, Kotlin 공식 호환 표에 명시된 Gradle 8.12.1로 Wrapper를 정렬했다. 메타데이터 검사를 끄거나 테스트를 생략하지 않는다. Wrapper JAR와 배포 ZIP의 SHA-256은 공식 체크섬과 대조했다. 최종 실행 결과는 status.md에 기록한다.
