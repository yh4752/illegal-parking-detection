O1 개념부터 이해하기 — 운영 프로필·DB 권한·MQTT 보안

2026-11-16 · O1 로컬 구현·인수 범위 · 외부 배포 없음

운영 설정은 프로그램이 무엇에 접속할지와 어디까지 할 수 있을지를 제한하는 장치다. 프로그램이 켜지는 것만으로는 충분하지 않다. 잘못된 서버에 연결하거나, 다른 장치의 메시지를 보내거나, 실행 계정으로 DB 구조까지 바꿀 수 있으면 사고 범위가 커진다.

이 안내는 개념과 이해 확인을 위한 문서다. 실제 파일 이름·계정 생성·명령은 운영 설정 설명서, 실행 결과는 O1 검증 기록을 따른다. O2~O4가 뒤에 추가됐지만 이 문서는 O1이 해결하는 문제에 집중한다.

1. 장치가 사건 하나를 보낼 때 통과하는 문

TLS 서버 확인 → MQTT 계정 인증 → 토픽 권한 확인 → 사건 내용 검증 → DB 커밋 → 응용 ACK

확인 단계 묻는 질문 거절되는 예
TLS 통신이 암호화되고, 내가 의도한 브로커인가? 신뢰하지 않는 CA, 접속 이름과 다른 인증서
계정 인증 이 연결은 등록된 MQTT 계정인가? 익명 접속, 잘못된 비밀번호
ACL 이 계정이 이 토픽에 읽기/쓰기를 해도 되는가? 장치 A가 B의 토픽에 쓰기, 자기 ACK 위조
업무 검증 내용·장치 등록·순서가 제품 계약에 맞는가? 올바른 계정이 보낸 잘못된 사건 내용
DB 권한·커밋 이 작업을 허용하는 계정으로 실제 저장했는가? runtime의 DDL, DB 실패 뒤 성공 ACK

앞 단계를 통과해도 다음 단계가 보장되는 것은 아니다. TLS로 암호화된 잘못된 사건도 거부해야 하고, DB에 저장했어도 ACK 발행이 실패할 수 있다. MQTT의 PUBACK와 우리 제품의 STORED·DUPLICATE 응용 ACK는 구별한다. ACK 실패의 실제 발견은 O3 설명에 있다.

2. TLS, 비밀번호, ACL은 왜 모두 필요한가?

TLS는 통신을 보호하고 접속 대상 서버를 확인한다. CA는 인증서의 서명자를 신뢰하는 기준이고, SAN은 인증서가 유효한 서버 이름이다. CA가 맞아도 이름이 다르면 접속을 거부한다. 현재 MQTT 구성의 장치 계정 인증은 사용자 이름·비밀번호 방식이며, TLS를 쓴다고 장치별 클라이언트 인증서를 발급한 것은 아니다.

비밀번호는 어떤 MQTT 계정인지 확인한다. 비밀번호가 맞는 계정에 모든 토픽을 허용하면 다른 장치를 흉내 낼 수 있으므로 ACL로 읽기·쓰기 범위를 더 제한한다. edge-01은 자기 events/heartbeat/availability를 쓰고 자기 acks를 읽는다. 서버는 그 반대 방향을 담당한다. 장치의 자기 ACK 쓰기는 허용하지 않는다.

빠진 장치 남는 문제
TLS·서버 이름 검증 통신 보호 또는 올바른 상대 확인이 사라짐
계정 인증 접속자가 누구인지 구분하지 못함
토픽 ACL 인증된 장치가 다른 장치 영역에 접근할 수 있음
업무 검증 허용된 토픽에 잘못된 내용이 저장될 수 있음

첫 공개에서 외부 MQTT 8883을 열지 않는 결정은 이 검사를 대체하지 않는다. 외부 접속 경로를 줄이는 일과 내부 연결의 권한을 제한하는 일은 함께 적용한다.

3. DB 계정을 네 개로 나누는 이유

프로그램이 평소 필요한 권한과 사람이 구조를 변경하거나 계정을 관리할 권한은 다르다. 웹 요청을 처리하는 프로세스에 관리자 암호를 주면 그 프로세스의 오류가 DB 전체 변경으로 이어질 수 있다.

DB 계정 언제 사용하는가? 허용하는 일 허용하지 않는 대표 작업
migrator 배포 전 별도 일회성 실행 스키마 생성·마이그레이션 평상시 웹 요청 처리에 자격증명을 공급하지 않음
runtime 백엔드가 계속 실행될 때 조회·사건 저장·receipt·상태 갱신·정해진 보관 만료 삭제 DDL, 정책·웹 계정 변경, 사건 원문 임의 수정
operator 운영자가 웹 계정을 관리할 때 사용자·구역 접근 권한·감사 기록 관리 스키마 변경이나 범용 복원 관리자 역할
backup 백업 작업 테이블 읽기와 dump 업무 데이터 쓰기·DDL

runtime은 읽기 전용이 아니다. 필요한 쓰기를 구체적으로 허용하는 계정이다. 역할을 나누면 암호와 실행 경로를 관리하는 부담이 늘지만, 한 프로세스가 불필요한 권한을 갖는 것을 줄인다. DB 계정 네 개와 웹의 VIEWER/OPERATOR는 다른 층의 권한이다.

관리자 접속 후 SET ROLE만 하면 충분할까?

session_user는 처음 로그인한 계정이고 current_user는 현재 명령에 적용되는 역할이다. 관리자 계정으로 로그인한 뒤 SET ROLE parking_runtime만 하면 현재 역할은 낮아 보여도 로그인 자격은 관리자다. O1에서는 실제로 runtime으로 로그인했는지까지 검사하도록 했다. 검증도 관리자 연결에서 역할만 바꾸는 시험을 실제 제한 계정 로그인으로 고쳤다.

또한 SELECT FOR UPDATE 같은 행 잠금에는 추가 UPDATE 권한이 필요했다. 그래서 전체 테이블 UPDATE를 허용하는 대신 필요한 열의 권한과 제약을 확인했다. 이 선택과 불필요한 원문 UPDATE 권한 제거가 검토·수정 기록의 review_fixes에 남아 있다.

4. 운영 프로필과 파일 secrets

Spring 프로필은 실행 설정 묶음을 고른다. app-prod는 우리 프로젝트가 정한 묶음 이름이다. 이름에 prod가 있다고 보안이나 배포가 자동으로 완성되는 것은 아니다. 이 프로필에서는 로컬 프로필 혼용, 자동 migration, 평문 MQTT, 잘못된 DB 역할 등을 거부하도록 코드로 검사한다.

파일 secrets는 비밀번호를 소스 코드·공유 설정에서 분리하고 필요한 서비스에만 읽기 전용으로 전달하는 방법이다. Compose가 원본 파일을 자동으로 암호화하는 기능은 아니다. 호스트 파일 권한과 복구용 키 보관은 따로 필요하다.

현재 구현은 필수 secret 파일이 없으면 환경변수의 값으로 조용히 대신 실행하지 않는다. 파일 값과 최종 설정이 달라도 중단한다. 잘못 배포한 설정을 정상 운영으로 오인하는 대신 기동 실패로 드러내는 선택이며, 비밀값 교체 때 파일·권한·재기동 절차를 관리해야 하는 부담이 있다.

5. 코드와 시험에서 직접 확인하기

먼저 아래 파일을 읽고, “허용할 것”과 “거부할 것”을 각각 하나씩 찾는다. 암호 파일을 열거나 내용을 공유할 필요는 없다.

파일 찾을 내용

RevisionConfiguration 실제 DB의 session_user/current_user와 역할 권한을 어디서 검사하는가?
역할 생성 SQL·권한 SQL runtime과 backup의 권한 차이는 무엇인가?
Mosquitto ACL 장치는 왜 자기 acks를 쓰지 못하는가?
MQTT TLS 설정 CA와 서버 이름 검증은 어디에 적용되는가?
O1 인수 시험 잘못된 인증서·계정·타 장치 접근을 실제로 시험하는가?

실행하려면 운영 설정 설명서의 준비 조건을 따른다. 아래 명령은 별도 임시 프로젝트에서 실제 거부·정상 저장 경로를 시험한다. 캐시가 있으면 약 2~4분이며, 첫 빌드는 더 걸린다. 기존 DB의 계정이나 ACL을 수동으로 바꾸는 실습이 아니다.

python3 tools/production/verify_o1.py

성공 마지막 문구는 O1_ACCEPTANCE_PASSED다. 시험 이름별 PASS:는 해당 관찰의 증거이고, 전체 성공도 공인 HTTPS나 외부 배포 성공을 뜻하지 않는다.

6. 이해 확인 — 먼저 자기 말로 답하고 확인하기

첫 답은 개인 메모에 남긴다. 모르는 부분은 그대로 표시한다. 아래 점검 기준은 정답을 외우기 위한 문장이 아니라 빠뜨린 개념을 찾기 위한 것이다. 이 문서를 추가했다고 학습자가 이미 이해하거나 실습을 완료했다고 기록하지 않는다.

질문 답변에서 확인할 핵심
TLS가 켜져 있는데 왜 비밀번호와 ACL이 더 필요한가? 상대 서버·계정 식별·토픽 권한의 차이
신뢰하는 CA의 인증서인데 접속 이름이 다르면 왜 거부할까? 다른 서버의 정상 인증서를 잘못 신뢰하지 않도록 이름도 확인
장치가 자기 ACK 토픽에 쓸 수 있으면 어떤 문제가 생길까? 저장 결과를 장치 스스로 위조할 수 있는 경로
runtime을 읽기 전용으로 만들면 왜 사건 저장이 안 될까? 최소 권한은 권한 0이 아니라 필요한 작업만 허용하는 것
DB operator와 웹 OPERATOR는 같은 계정인가? DB 관리 작업 자격과 제품 사용자 역할의 차이
관리자 로그인 후 SET ROLE은 실제 runtime 로그인과 무엇이 다른가? session_user와 current_user, 남아 있는 로그인 자격
파일 secret이 없는데 환경변수 값으로 실행되면 어떤 배포 실수를 놓칠까? 파일 전달 누락·설정 불일치가 숨겨지는 문제
backup 계정으로 dump가 성공하면 복구까지 증명됐나? 암호화 키·실제 restore·내용 비교·최신 revision 대조는 별도
MQTT PUBACK를 받으면 DB 저장과 장치 처리가 모두 끝난 것인가? 브로커 수락·DB 커밋·응용 ACK·장치 처리 경계
외부 포트를 닫았으니 내부 인증을 제거해도 될까? 노출 경로 축소와 내부 계정 권한은 다른 방어

확인한 뒤에는 “우리 시스템에서 막으려던 실수 하나 → 적용한 제한 → 실제 거부 시험 → 남는 한계” 순서로 30~60초 설명해 본다. 자신의 답변·모르는 부분은 공개 저장소에 자동으로 올리지 않는다.
