# 백업·증거 보존·복구 목표와 단독 관리

**2026-11-19 구현 상태:** 승인한 목표를 변경하지 않는다. [외부 저장 구현](external-storage-preparation.md)에 일별 DB 백업/5분 로그 복사 timer 예시와 별도 외부 백업 지표를 추가했다. timer 설치·외부 알림·7세대 삭제·실제 키 회수는 미완료다. 새 경로는 age 공개 recipient만 서버에 두고 개인 identity는 기존 금고/USB 정책에 따라 별도 보관한다. 기존 Fernet 키는 해당 보존 파일이 남는 동안 함께 유지한다. 실제 운영 키 생성·보관 장소 확정은 하지 않았다.

2026-11-17 · **사용자 승인 목표와 본인 단독 관리 기준. 외부 자동화·복구 인수는 미완료**

가상 사건 데이터는 장애 후 다시 만들 수 있다. 발표·블로그에 쓰는 원래 로그·캡처·검증 수치는 반드시 보존한다. 다시 실행한 시험의 결과로 과거 증거를 대체하지 않는다. 이 구분을 바탕으로 아래 주기·목표·보관 기간을 승인했다. 구매, 계정·버킷·금고·DNS 생성, 외부 배포, 예약 작업 설치는 승인하거나 수행하지 않았다.

전체 준비는 [O5 결정표](deployment-readiness.md), 후속 구현은 [이슈 #6](https://github.com/yh4752/illegal-parking-detection/issues/6)에서 추적한다. 목표 승인으로 F1 전체 또는 F2~F6이 완료되지는 않는다.

## 1. 승인한 주기와 목표

RPO는 잃어도 되는 최근 자료의 범위, RTO는 다시 사용할 수 있을 때까지 허용하는 시간이다. 서비스 복구, 증거 회수, 발표 계속하기를 별도 목표로 관리한다. 아래 값은 공급자의 보장이나 이미 측정한 성과가 아니다. [AWS 복구 목표 안내](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/plan-for-disaster-recovery-dr.html)

| 대상 | 주기·처리 시점 | 승인한 목표 |
|---|---|---|
| 가상 사건 DB | 매일 03:00 KST, 배포·DB 변경 직전, 운영 종료 전 | 최근 24시간 손실 허용. 서비스 복구 2시간 이내 |
| 발표·블로그 증거 | 캡처·측정 결과 생성 즉시 저장, 성공·실패 시험마다 종료 직후 별도 보존 | 보존 완료된 증거의 손실 0 목표. 다른 환경에서 회수·열람 15분 이내 |
| 실행 중인 로그 | 최소 5분마다 서버 밖 복사, 종료 시 최종본 보존 | 복사 전 최근 최대 5분 손실 가능 |
| 독립 revision 기록 | 범위 예약·최신 기준 갱신 때마다 외부에 동기 반영한 후 성공 처리 | 성공한 예약의 손실 0 목표. 최신성 확인 불가 시 수신/API 보류 유지 |
| 발표 대체 시연 | 12월 10일까지 로컬 실행판 또는 녹화 시연·발표 자료를 준비하고 인터넷 없이 연습 | 발표 중 장애 시 5분 이내 전환. 녹화는 녹화임을 표시 |

DB 백업은 일관된 스냅샷, 암호화 외부 사본, 무결성 확인이 성공해야 최근 성공 시각을 갱신한다. 매일 실행한다는 설정만으로 RPO 24시간을 달성한 것으로 보지 않는다. 실패·지연으로 최신 성공 백업이 24시간보다 오래되면 목표 위반을 알리고 재시도하며, 실패한 백업은 정상 세대를 밀어내지 않는다. 실행 중 로그도 마지막 외부 복사 성공 이후 5분을 넘으면 목표 위반으로 기록한다. 이 감시·알림은 후속 구현이다.

서비스 RTO 2시간은 **서비스 중단부터 HTTPS 로그인과 새 가상 사건 갱신이 다시 가능할 때까지**다. 인지·대응, 계정·키 회수, 다운로드, 서버 준비, DB 복원, 최신 revision 대조·명시 인수 시간을 포함한다. 증거 회수 15분은 원래 서버를 사용할 수 없는 상태에서 회수를 시작해 복호화·해시 확인 후 파일을 열 때까지다. 발표 전환 5분은 장애로 시연이 중단된 시점부터 대체 자료로 설명을 계속할 때까지다.

## 2. 증거를 보존 완료로 표시하는 조건

각 시험의 실행 ID·시각별로 다음을 한 묶음으로 만든다.

- 성공과 실패를 포함한 원본 로그, 캡처, 가공 전 측정값과 요약 수치
- 코드 커밋, 이미지 식별자, 실행 환경·명령, 시작·종료 시각과 측정 조건
- 파일 목록과 SHA-256 해시, 공개용 사본을 만들었다면 가림·변환 내역

작업용 사본 외에 **서로 독립된 두 곳으로 복사하고, 각 사본을 다시 읽어 해시·파일 열람이 되는지 확인**해야 보존 완료로 표시한다. 후보 구성은 작업 PC + 별도 계정의 비공개 S3 + 다른 물리 장소에 분리 보관한 오프라인 매체다. 같은 PC의 폴더 두 개, 계속 연결된 같은 장소의 매체만으로 독립 사본 둘을 충족했다고 판단하지 않는다. 독립 사본을 확인하기 전 원본을 정리하지 않는다. 저장소·매체의 실제 선택과 접근 검증은 아직 남아 있다.

손실 0은 보존 완료된 묶음에 대한 목표다. 생성 중인 자료, 아직 외부 복사가 끝나지 않은 로그까지 무손실을 보장하지 않는다. 중요한 측정 후에는 보존 확인을 다음 시험이나 환경 정리보다 먼저 수행한다. 보존이 실패하면 시험 결과와 보존 실패를 함께 기록하며 보존 완료로 표시하지 않는다.

원본에 자격증명·개인정보가 포함되면 비공개 암호화 사본으로 제한하고 GitHub에는 가림 처리한 공유본만 남긴다. 가림으로 측정값을 바꾸지 않는다. Git 이력과 CI 로그·첨부파일·PR/Checks 정보의 보관 범위는 다르므로 필요한 CI 자료와 메타데이터도 별도 묶음에 넣는다. 현재 [CI 설정](../.github/workflows/verify.yml)의 첨부파일 보관은 7일이다. GitHub에 링크만 남기는 것은 증거 파일의 장기 보존을 대신하지 않는다. [GitHub 저장소 백업 안내](https://docs.github.com/en/repositories/archiving-a-github-repository/backing-up-a-repository)

## 3. 승인한 보관 기간

| 자료 | 보관 기준 |
|---|---|
| 일상 DB 백업 | 최근 성공한 일별 7세대 |
| 변경 직전·최종 DB 백업 | 필요한 변경 직전 사본을 일반 순환에서 별도 보호. 최종본은 2027-01-10까지 보관 후 필요성을 검토 |
| 발표·블로그 증거 | 최소 2027-12-11까지, 이후에도 발표·블로그·포트폴리오에서 쓰는 동안 유지. 자동 삭제 없음 |
| 최종 revision 기록 | 증거와 함께 최소 2027-12-11까지, 복원 가능한 백업이 더 오래 남으면 그 기간까지 최신 기준과 필요한 이력을 보존 |
| 암호화 키 | 그 키를 필요로 하는 마지막 백업·증거 파일이 남아 있는 동안 보관. 키 교체 후에도 옛 파일에 필요한 옛 키 유지 |

날짜 도달은 자동 삭제 승인이 아니다. 일반 DB 순환 규칙을 증거·revision에 복사하지 않는다. S3 버전 이력의 이전 사본도 용량·요금 계산에 포함한다. [S3 Versioning](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Versioning.html)

발표 후 장기 증거 보관까지 2026-11-18 변경한 총 5만 원 계획에 포함해 검토한다. S3의 저장·버전·요청량과 오프라인 매체 확보 여부를 실제로 확인하기 전 비용 충족을 단정하지 않는다. 12월 11일 서버 운영 종료와 증거 보관 종료는 서로 다른 일정이다.

## 4. 계정·키는 본인이 단독 관리한다

사용자는 보조 담당자 없이 **본인 한 명이 관리**하기로 했다. 공개 문서에는 역할만 기록하고 계정 이메일·결제 정보·키·복구 코드·보관 장소의 상세는 넣지 않는다. 운영/백업 AWS 계정 분리와 Bitwarden 무료 개인 금고·암호화 USB·종이 복구 안내서 구성은 승인했다. 실제 계정 생성·매체 확보·보관 장소·접근 시험은 미완료다.

| 책임 | 담당 | 준비할 내용 |
|---|---|---|
| 백업 계정 소유·접근 관리 | 본인 | 운영 계정과 분리하는 것으로 확정한 백업 계정(미생성), 지속 사용 가능한 이메일·복구 경로·MFA. 납부자와 결제 수단은 별도 확정 |
| 백업 운영·증거 인수 | 본인 | 실패·용량·비용 확인, 두 독립 사본의 해시 확인, 정리 전 보존 완료 확인 |
| 암호화 키 주 사본 | 본인 | 서버 밖 Bitwarden 무료 개인 금고로 확정(미생성). 공유 조직·공유 로그인 불필요 |
| 키·로그인 추가 복구 수단 | 본인 | 암호화 USB와 별도로 보관하는 종이 복구 안내서. 실제 장소는 미정. 주 기기·금고 없이도 회수할 수 있도록 준비 |
| 복원·발표 대체 시연 | 본인 | 원래 서버·주 로그인 기기 없이 추가 수단으로 회수·복원하는 시험과 발표 전환 연습 |

계정 수와 담당자 수는 다르다. 한 사람이 운영하며 운영용 AWS 계정과 백업용 AWS 계정을 분리하기로 확정했다. 계정 분리는 운영 계정의 실수·권한 오용이 백업 관리까지 번지는 범위를 줄인다. 같은 이메일 계정·기기·금고의 침해가 양쪽 접근으로 이어질 수 있어 복구 경로도 확인해야 한다. 실제 계정·이메일·결제·접근 경로는 아직 준비하지 않았다. [AWS 계정 분리 지침](https://docs.aws.amazon.com/wellarchitected/latest/framework/sec_securely_operate_multi_accounts.html)

소유자 접근, 일상 관리, 서버 자동 작업의 권한을 나눈다. root는 필요한 소유자 작업에만 쓰고 서버에 root 자격이나 백업 관리자 권한을 두지 않는다. 자동 업로더에는 필요한 업로드·검증 읽기만, revision 런타임에는 필요한 읽기·조건부 갱신만 주며 삭제·보존 설정 변경은 금지하는 안이다. 실제 권한 거부 시험이 필요하다. [AWS root 관리 지침](https://docs.aws.amazon.com/IAM/latest/UserGuide/root-user-best-practices.html)

O4는 대칭키로 백업을 만들기 때문에 제한된 작업용 키가 서버에도 필요하다. 서버 밖 사본은 키 유실 대비이며, 서버 침해 시 작업용 키 유출 위험까지 없애지는 않는다. 본인이 부재하거나 대응할 수 없으면 대신 복구할 사람이 없다. 서비스 복구 2시간 목표는 그대로 유지하며, 본인의 대응 가능 여부와 실제 시험으로 달성 가능성을 판단한다. 이 한계를 숨기거나 목표 측정 시작을 복원 명령 시점으로 늦추지 않는다.

## 5. 승인한 보관 구성과 남은 결정

| 구성 | 담을 내용 | 장소·비용·남는 위험 |
|---|---|---|
| Bitwarden 무료 개인 금고 | AWS 계정 정보, 백업 키와 식별자·사용 시점 | 서버 밖 주 사본. 계정 미생성. 무료 요금제의 보안 메모 사용. 로그인 불가·잠금 해제 기기 침해에 대비한 추가 사본 필요 |
| 암호화 USB | 복구에 필요한 키·절차와 비밀번호 보호 금고 내보내기 | 평소 연결하지 않고 작업 기기와 다른 물리 장소의 잠금 공간에 보관. 실제 장소·보유 매체·암호화 도구 미정. 분실·고장·갱신 누락 위험 |
| 종이 복구 안내서 | 금고 로그인 주소·이메일, 마스터 비밀번호, 금고 2단계 인증 복구 코드, USB 복호화 비밀번호와 복구 순서 | USB와 분리한 잠금 공간에 봉인 보관. 실제 장소 미정. 원격 해킹 노출을 줄이지만 도난·화재·오타 위험. 봉투는 개봉 흔적 확인용이지 도난 방지 장치가 아님 |

무료 금고와 보유 매체로 시작할 수 있지만 매체·잠금 공간이 없으면 추가 비용을 확인한다. 계정 분리 자체의 추가 이용료와 S3 저장·버전·요청·전송 비용을 구분하고, 발표 후 증거 보관도 2026-11-18 변경한 총 5만 원 계획에 포함해 다시 계산한다. 금고와 키 사본은 로그·캡처·수치 파일의 두 독립 사본을 대신하지 않는다. 증거 보관 매체와 키 보관 매체의 배치도 별도로 결정한다.

금고 내보내기는 원래 계정에 묶인 Account restricted 대신 별도 비밀번호를 사용하는 Password protected 방식을 사용한다. 내보내기 비밀번호가 잠긴 금고에만 있거나 USB와 같은 봉투에 있지 않도록 한다. 금고의 2단계 인증 복구 코드는 마스터 비밀번호를 대신하지 않으며, 금고 제공자가 잊은 마스터 비밀번호를 복구해 주지는 못한다. 종이 안내서·키·복구 코드는 공개 Git/이슈·채팅에 넣지 않는다. [무료 요금제](https://bitwarden.com/help/password-manager-plans/), [암호화 내보내기](https://bitwarden.com/help/encrypted-export/), [복구 코드](https://bitwarden.com/help/two-step-recovery-code/), [마스터 비밀번호 분실](https://bitwarden.com/help/forgot-master-password/)

추가로 결정할 항목은 다음과 같다. 현재는 모두 미정이며 이 목록은 생성·구매 승인이 아니다.

1. 백업 계정의 이메일·복구 연락처, 비용 납부자·결제 수단, 독립 계정/Organizations 관리 방식과 일상 접근 경로. 분리 여부 자체는 확정이다.
2. Bitwarden 계정 이메일·서비스 지역, 인증 앱 또는 보안키 등 실제 2단계 인증 방식과 이메일/AWS 로그인 복구 수단. 금고 로그인에 필요한 수단을 금고 안에만 두지 않는다.
3. 사용할 USB의 보유 여부·상태·용량, 암호화 도구와 다른 PC에서 열 수 있는지, 추가 비용. 실제 키를 만들기 전에 복구 호환성을 확인한다.
4. USB와 종이를 둘 서로 분리된 잠금 공간, 본인 접근 시간·이동 시간·분실/화재 위험. 공개 문서에는 장소 별칭만 기록하고 현재 값은 미정으로 둔다.
5. 증거 원본의 독립 오프라인 사본 위치·용량과 키 매체와의 분리 방식. 키만 보관하고 증거 파일 보존이 끝났다고 판단하지 않는다.
6. 사본 점검 일정과 회수 시험 일시. 키·비밀번호·복구 수단 변경 직후 사본을 갱신하고, 옛 암호화 파일에 필요한 옛 키는 유지한다.

원래 서버·주 로그인 기기 없이 신뢰할 수 있는 다른 기기에서 회수·복호화·해시·열람을 시험한다. 금고까지 접근할 수 없는 경우 USB·종이 회수와 이동 시간도 증거 회수 15분 측정에 포함한다. 장소 때문에 목표를 넘으면 미달로 기록하며, 목표를 자동 완화하거나 이동 시간을 빼지 않는다. 서비스 중단부터 2시간 목표와 본인 부재 한계도 유지한다. 실제 장소 결정과 시험 전에는 목표 달성을 주장하지 않는다.

## 6. 지금 확인한 것과 아직 남은 것

2026-11-17 로컬에서 기존 manifest의 증거 28개 SHA-256을 확인했다. 해당 시점 Git이 추적하는 `validation/`·`docs/screenshots/` 50개 파일은 합계 1,286,852바이트였다. 이 값은 기존 자료 규모이며 이후 운영 로그 증가량이나 원격 보관 비용을 예측한 값이 아니다. 근거 경로는 [학습·증거 모음](operations-learning-evidence.md)을 따른다.

자동 백업·외부 사본·5분 로그 복사·보존 정책·실제 권한·개인 금고/추가 키 사본·15분 회수·2시간 복구·5분 발표 전환은 아직 구현 또는 인수하지 않았다. 로컬 백업 도구에는 128MiB 제한이 있다. 기존 로컬 복원~준비 85.65초와 100.30초는 인지·계정 회수·서버 준비 등을 포함하지 않아 전체 RTO의 증거가 아니다. 과거 실행 기록과 이미 보존한 파일을 새 시험 결과로 덮어쓰지 않는다.
