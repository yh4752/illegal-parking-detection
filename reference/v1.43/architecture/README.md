# 아키텍처와 동작을 읽는 방법

v1.43 · v1.42의 17개 그림을 텍스트로 옮긴 자료다. 구현·설치·실험 완료를 뜻하지 않는다.

이 폴더의 Mermaid 파일은 구성과 순서를 설명한다. 각 파일 맨 위의 `Rule` 주석과 연결된 상세 명세를 함께 읽는다. 그림에 생략된 조건을 새로운 기본값으로 해석하지 않는다. 필드·상태·시간·물리 출력 규칙이 상세 명세와 충돌하면 임의로 선택하지 않고 충돌 위치와 영향을 보고한다.

## 필요한 그림부터 읽기

| 알고 싶은 것 | 읽을 그림 |
|---|---|
| 사용자·서비스 범위 | F01 |
| 전체 앱·저장소와 통신 방향 | F02, F05 |
| 백엔드 내부 책임 | F03, F07~F12, F17 |
| 엣지의 AI·SDK 결합과 출력 | F04, F06, F10, F15, F16 |
| 웹 상태와 관리자 명령 | F08, F09 |
| 담당과 인계·일정 | F13, F14 |

C4의 L1은 시스템 맥락, L2는 애플리케이션·저장소, L3는 한 애플리케이션 안의 책임 구분이다. 실제 호스트·포트는 배포도 F05에 둔다. Container는 Docker 컨테이너와 동의어가 아니다. 구현 전이므로 L4의 클래스·함수 구조는 확정하지 않았다.

이 문맥의 **C4 모델**과 `spec/protocol/C4.md`의 **C4 절번호**는 서로 다르다. 후자는 ‘명령과 실행 결과의 계약’을 뜻한다.

## 구성요소와 책임

| 요소 | C4 구분 | 책임 | 실행·저장 위치 |
|---|---|---|---|
| 운영 관리자 / 조회 사용자 / 운전자 | Person | 제어·조회 / 조회 / 현장 안내 수신 | 관리자 브라우저 / 현장 |
| 엣지 AI 주정차 안내 시스템 | Software system | 정차 관찰, 현장 안내, 상태·이력 관리 | 아래 앱·저장소를 포괄 |
| 관리자 웹 | Container | React·TypeScript, 요청·상태·최신성 표시 | 관리자 브라우저 |
| 백엔드 | Container | Kotlin·Spring Boot, 권한·검증·DB·명령·REST/SSE | 개발 PC 또는 Linux 서버 |
| 메시지 브로커 | Container | Mosquitto, MQTT 5/TLS 중계·인증·토픽 ACL | 시연 시 서버와 같은 호스트의 다른 프로그램 |
| 엣지 앱 | Container | AI 제어와 백엔드 작성 SDK를 같은 프로세스에서 결합 | QCS610 보드 |
| PostgreSQL | Container/데이터 저장소 | 사건·상태·정책·명령·서버 outbox | 서버의 영속 볼륨 |
| 서버 사진 파일 | Container/파일 저장소 | 권한이 제한된 JPEG, DB에 메타데이터 | 서버의 영속 볼륨 |
| SQLite / 사진 대기함 | Container/로컬 저장소 | checkpoint·outbox / 미전송 JPEG | 보드에서 엣지 앱이 직접 접근 |

컴포넌트 내부의 책임은 F03·F04, 개발 담당은 F13을 따른다. 서버의 Kotlin을 보드 SDK의 확정 언어로 해석하지 않는다. 보드 OS·ABI·지원 라이브러리 확인 후 SDK 언어와 바인딩을 정한다.

## 주요 관계

| 송신·호출 주체 | 수신·사용 대상 | 방식 | 내용 |
|---|---|---|---|
| 웹 | Spring | HTTPS REST | 조회·정책·제어 요청 |
| Spring | 웹 | HTTPS SSE | DB 커밋 후 ZoneView |
| 엣지 앱 | Mosquitto → Spring | MQTT 5/TLS | 사건·heartbeat·명령 결과·reported |
| Spring | Mosquitto → 엣지 앱 | MQTT 5/TLS | 응용 ACK·명령·desired 정책 |
| 엣지 앱 | Spring | HTTPS | JPEG 사진 업로드 |
| Spring | PostgreSQL / 사진 파일 | JDBC / 파일 I/O | 업무 저장 / 비공개 사진 |
| AI 제어 | SDK | 내부 함수 호출·비동기 완료 통지 | 상태 전이·명령·사진 작업 |
| SDK | SQLite / 로컬 파일 | 로컬 저장 | 상태·횟수·메시지·outbox / JPEG |

배포 시 Nginx는 React 정적 파일을 제공하고 API·SSE·사진 요청을 Spring으로 프록시한다. 원본 영상이나 매 프레임 탐지 상자를 서버에서 재분석하는 경로는 없다.

## 그림별 원본과 상세 기준

### F01 · 사용자와 시스템의 관계

[Mermaid 원본](F01.mmd) · 이전 그림: v1.42 F01

상세 기준: [project/01](../spec/project/01.md) · [roles/B1](../spec/roles/B1.md)

- 운전자는 별도 앱 없이 현장 안내를 받는다. 법적 위반 확정·과태료 부과·자동 신고는 범위에서 제외한다.

### F02 · 서비스를 구성하는 애플리케이션과 저장소

[Mermaid 원본](F02.mmd) · 이전 그림: v1.42 F02

상세 기준: [project/10](../spec/project/10.md) · [protocol/C15](../spec/protocol/C15.md) · [roles/B2](../spec/roles/B2.md)

- C4 Container는 애플리케이션 또는 저장소다. Docker 컨테이너 및 실제 호스트 배치는 F05와 구분한다.
- SQLite와 사진 대기함을 별도 DB 서버 또는 별도 프로세스로 해석하지 않는다. SDK의 실제 언어와 바인딩은 보드 환경 확인 후 결정한다.
- 원본 영상이나 매 프레임 탐지 상자를 서버에서 다시 분석하지 않는다. 사진은 HTTPS, 사건·명령은 MQTT 경로다.
- 서버와 브로커의 각 화살표는 발행·구독 관계다. 직접 웹↔장치 연결을 추가하지 않는다.

### F03 · Spring 내부의 책임과 호출 관계

[Mermaid 원본](F03.mmd) · 이전 그림: v1.42 F03

상세 기준: [protocol/C14](../spec/protocol/C14.md) · [protocol/C15](../spec/protocol/C15.md) · [protocol/C17](../spec/protocol/C17.md) · [storage/D5](../spec/storage/D5.md) · [storage/D6](../spec/storage/D6.md)

- 웹 API·사진 API는 웹/장치 인증 경로를 구분한다. MQTT 어댑터는 브로커, 저장소 접근은 PostgreSQL, SSE 전달은 관리자 웹과 연결한다.
- 사진 파일 I/O는 DB 행 잠금 밖에서 수행한다. 서버 수신 성공 ACK와 SSE는 DB 커밋 뒤에 전송한다.
- Actuator·Micrometer와 구조화 로그로 관찰한다. 그림의 컴포넌트는 책임 구분이며 별도 서버나 확정 클래스명이 아니다.
- 구체적인 중복 처리, 구역 잠금, outbox lease, 늦은 콜백 처리는 D5를 따른다. 그림의 화살표로 트랜잭션 경계를 추정하지 않는다.

### F04 · 같은 보드에서 결합하는 AI와 SDK

[Mermaid 원본](F04.mmd) · 이전 그림: v1.42 F04

상세 기준: [roles/B2](../spec/roles/B2.md) · [roles/B3](../spec/roles/B3.md) · [storage/D3](../spec/storage/D3.md)

- AI는 판단 상태와 실제 출력 제어를 소유한다. SDK는 통신·저장 공통 코드이며 백엔드가 작성하고 AI가 실제 보드에 설치·결합한다.
- restore, commit_transition, take_command의 정확한 입력·결과와 버전 규칙은 B2 및 개발자료 07 계약을 따른다. 별도 HTTP 서비스나 IPC를 추가하지 않는다.
- SDK 언어·바인딩은 아직 정하지 않았다. PC 모의 어댑터는 백엔드, 실물 어댑터는 AI가 담당한다.
- 카메라 읽기·추론·JPEG 인코딩·네트워크·fsync가 AI 제어 루프를 막지 않아야 한다. JPEG와 촬영 시각은 AI가 제공한다.
- 새 안내는 저장 완료와 현재 조건 재검사 후 시작한다. 안전 중단은 저장을 기다리지 않는다. F10을 함께 읽는다.

### F05 · 장치·브라우저·서버의 실제 배치

[Mermaid 원본](F05.mmd) · 이전 그림: v1.42 F05

상세 기준: [project/10](../spec/project/10.md) · [protocol/C16](../spec/protocol/C16.md) · [protocol/C17](../spec/protocol/C17.md)

- Nginx가 React 정적 파일을 브라우저에 제공하며 React 코드는 브라우저에서 실행된다. Nginx→Spring 화살표의 실제 프록시 대상은 API·SSE·사진 업로드다.
- 서버와 브로커는 같은 호스트의 서로 다른 프로그램이다. DB·사진·브로커 데이터는 영속 볼륨에 둔다.
- 허가한 HTTPS 443와 MQTT/TLS 8883만 외부 공개 대상으로 삼는다. Spring 8080, DB 5432, 관리 포트를 외부에 직접 열지 않는다.
- Prometheus/Grafana는 선택 모니터링 프로필이다. Actuator·구조화 로그는 기본 관찰 항목이다.
- 단일 호스트 구조다. 고가용성이나 무중단 배포를 보장하지 않는다. 보드 OS·ABI·카메라·배선·SDK 바인딩·서버 실제 주소는 확인이 남아 있다.

### F06 · 첫 안내·재안내·미해소는 서로 다른 시계다

[Mermaid 원본](F06.mmd) · 이전 그림: v1.42 F06

상세 기준: [project/07](../spec/project/07.md) · [protocol/C3](../spec/protocol/C3.md) · [protocol/A1](../spec/protocol/A1.md) · [protocol/A2](../spec/protocol/A2.md) · [protocol/A6](../spec/protocol/A6.md)

- 이 그림은 세 개의 독립적인 시간 기준이다. 시간 간격의 비율이나 고정된 330초 재안내를 뜻하지 않는다.
- 모든 재생 직전에 관측·동일성·품질·중지·출력·시각 등 현재 허용 조건을 검사한다. 정확한 guard와 시간 측정은 A1·A2·A6을 따른다.
- 600초 경계에서는 새 안내보다 미해소 처리를 우선한다. 600초 도달만으로 이미 재생 중인 음성을 중단하지 않는다.
- 이동·관측 실패·가림·중지로 후보가 초기화되어도 사건 ID·사용한 안내 횟수·고정된 미해소 기준은 유지한다.
- 5분은 이 프로젝트의 실험 안내 정책이며 법적 위반 확정 기준이 아니다.

### F07 · 브로커 수신 확인과 서버 저장 확인

[Mermaid 원본](F07.mmd) · 이전 그림: v1.42 F07

상세 기준: [protocol/C2](../spec/protocol/C2.md) · [storage/D1](../spec/storage/D1.md) · [storage/D2](../spec/storage/D2.md) · [storage/D5](../spec/storage/D5.md)

- PUBACK와 서버 전달 사이에는 선후 보장이 없다. PUBACK는 브로커의 수신 확인이고, 응용 ACK가 서버의 저장 확인이다.
- 응용 ACK를 잃으면 같은 message_id·본문·device_seq로 재전송한다. 메시지 재전송 때문에 음성을 다시 재생하지 않는다.
- DB 저장 실패에는 성공 ACK를 보내지 않는다. 같은 ID의 다른 내용은 격리하고 REJECTED로 응답한다.
- heartbeat는 5초 간격, QoS 0이며 응용 ACK를 요구하지 않는다. 그림은 durable 사건 메시지 경로를 설명한다.
- 최초 전송, 재접속, PUBACK 뒤 응용 ACK 대기와 outbox 완료·실패 전환의 상세 기한은 D1·D2를 따른다.

### F08 · 관리자 명령의 접수부터 적용 결과까지

[Mermaid 원본](F08.mmd) · 이전 그림: v1.42 F08

상세 기준: [protocol/C4](../spec/protocol/C4.md) · [protocol/C5](../spec/protocol/C5.md) · [protocol/C6](../spec/protocol/C6.md) · [storage/D2](../spec/storage/D2.md) · [storage/D5](../spec/storage/D5.md)

- 참여자를 줄여 표현했지만 SDK와 AI의 책임은 F04 및 B2·B3 그대로다. SDK가 실제 출력 성공을 추정하지 않는다.
- 202 QUEUED는 서버의 접수 완료다. PUBACK는 브로커 수신이며 APPLIED와 다르다.
- 원래 60초 명령 기한과 5초 결과 유예 뒤에도 실제 결과가 없으면 DELIVERY_TIMEOUT으로 기록한다. 적용 여부 미확인이며 미실행 또는 실행 실패로 단정하지 않는다.
- 즉시 STOP의 APPLIED는 논리 중지·드라이버 확인·결과 내구 저장을 뜻한다. 실제 물리 무음을 보증하지 않는다. 안전 중단 순서는 F10을 따른다.
- 예약 STOP의 APPLIED는 일정 등록 완료다. RESUME 후에도 다른 중지가 남으면 PAUSED를 유지한다. 늦은 실제 결과 처리와 확인 토큰 조건은 C4~C6을 따른다.

### F09 · 화면은 가장 큰 상태 버전만 반영한다

[Mermaid 원본](F09.mmd) · 이전 그림: v1.42 F09

상세 기준: [protocol/C8](../spec/protocol/C8.md) · [protocol/C15](../spec/protocol/C15.md)

- 최초 접속과 재연결 모두 SSE를 연결한 뒤 REST로 현재 상태를 조회한다. 연결 중 도착하는 SSE와 REST 응답에 같은 비교 규칙을 적용한다.
- 예를 들어 현재 12일 때 늦은 11은 무시하고 다음 13을 받으면 전체 값을 반영한다. 숫자는 설명용 예시다.
- 웹의 SSE 연결 상태와 장치 heartbeat 최신성은 별도로 표시한다. 새 heartbeat가 15초 초과 없으면 STALE, 30초 초과 없으면 OFFLINE이다.
- 마지막 snapshot이 빈 구역이었다고 해서 현재 구역도 비었다고 추정하지 않는다. 화면 상태의 최신성 표시는 C8을 따른다.

### F10 · 새 안내는 저장 후, 안전 중단은 즉시

[Mermaid 원본](F10.mmd) · 이전 그림: v1.42 F10

상세 기준: [roles/B3](../spec/roles/B3.md) · [protocol/A5](../spec/protocol/A5.md) · [storage/D3](../spec/storage/D3.md)

- 안전 stop과 LED off는 DB·네트워크·사진 작업을 기다리지 않는다. 위 두 경로를 하나의 저장 우선 규칙으로 합치지 않는다.
- 이전 안내의 COMMITTED가 늦게 도착해도 stop_generation이 바뀌었거나 현재 guard가 무효면 새 play를 실행하지 않는다.
- 이미 사용한 시도 횟수는 유지한다. 실행 확인과 필요한 내구 저장 없이 APPLIED를 보고하지 않는다.
- AI 제어 루프는 카메라 읽기·추론·JPEG 인코딩·fsync를 기다리며 멈추면 안 된다. SDK 단일 writer와 비동기 완료 통지의 상세는 D3를 따른다.

### F11 · 관련 DB 변경은 함께 저장하고 응답은 커밋 뒤에 보낸다

[Mermaid 원본](F11.mmd) · 이전 그림: v1.42 F11

상세 기준: [storage/D5](../spec/storage/D5.md)

- 두 상자는 서로 다른 작업 경로다. 한 트랜잭션이 양쪽 데이터를 모두 생성한다는 뜻이 아니다.
- DB는 READ COMMITTED이며 구역별 zone_view 행 잠금으로 동시 쓰기를 직렬화한다. 잠금 순서와 세부 변경 집합은 D5 및 transactions.txt를 따른다.
- 네트워크·파일 I/O 동안 DB 행 잠금을 유지하지 않는다. ACK 전송 실패가 이미 성공한 DB 커밋을 되돌리지 않는다.
- 현재 상태 순서와 과거 사건 이력 순서를 구분한다. 실제 결과가 먼저 도착했다면 늦은 발행 콜백으로 완료 상태를 되돌리지 않는다.

### F12 · 사진 파일과 DB는 세 단계로 맞춘다

[Mermaid 원본](F12.mmd) · 이전 그림: v1.42 F12

상세 기준: [protocol/C11](../spec/protocol/C11.md) · [storage/D6](../spec/storage/D6.md)

- 사진 파일과 PostgreSQL은 하나의 ACID 트랜잭션이 아니다. A·C는 짧은 DB 트랜잭션이며 B는 행 잠금 밖의 파일 작업이다.
- 사진과 DB가 모두 내구 저장된 뒤에만 201/200을 응답한다. 재시작 시 복구 판정 전에는 새 업로드와 사진 정리를 일시 차단한다.
- 같은 image_id의 다른 내용은 충돌이다. 만료 사진은 즉시 접근을 차단하고 410을 반환하며 재시도로 보관기한을 연장하거나 사진을 되살리지 않는다.
- 이미 AVAILABLE인 사진을 늦게 도착한 FAILED로 되돌리지 않는다. 사진 실패가 사건 종료나 안전 중단을 지연시키지 않는다.

### F13 · 개발 담당과 코드 실행 위치

[Mermaid 원본](F13.mmd) · 이전 그림: v1.42 F13

상세 기준: [roles/B1](../spec/roles/B1.md) · [roles/B4](../spec/roles/B4.md) · [roles/B5](../spec/roles/B5.md)

- 개발 담당과 코드 실행 위치는 다르다. SDK가 보드에서 실행된다는 이유로 SDK 전체를 AI 담당의 개발 작업으로 옮기지 않는다.
- Data는 자료 출처·개발/평가 분할·정답·평가 분모와 결과를 관리한다. 실시간 MQTT 메시지 생성 책임은 없다.
- AI는 차량 탐지·추적·관측 품질·정차 판단, 카메라·시계·출력 어댑터, 모델 변환, 실제 보드 설치와 실물 출력을 맡는다.
- 백엔드는 공통 계약·통신/저장 SDK·가상 장치·서버·브로커·DB·배포·모니터링·통합 시험과 재현 절차를 맡는다.
- 프론트는 REST/SSE 연결과 상태·권한별 화면, 요청 접수·실제 적용·최신성의 구별을 맡는다. React 정적 파일은 Nginx가 제공한다.
- SDK 언어·바인딩과 보드 라이브러리 지원은 실제 환경 확인 후 확정한다.

### F14 · 개발과 검증의 단계별 완료 기준

[Mermaid 원본](F14.mmd) · 이전 그림: v1.42 F14

상세 기준: [plan/02](../spec/plan/02.md) · [plan/03](../spec/plan/03.md) · [roles/B5](../spec/roles/B5.md)

- D는 실제 착수일이며 D+일정은 달력일 기준의 잠정 목표다. 날짜가 지났다는 이유로 완료 또는 시험 통과로 처리하지 않는다.
- D+2에서 가용시간·제출일·작업량을 재산정한다. D+5의 보드 환경 확인은 W01, D+7 개발 자료 인계는 개발자료 05의 W14를 함께 따른다.
- D+14는 메시지·사진·명령 왕복의 통신 통합 목표다. 카메라·비전·실물 출력의 성능 완료와 구분한다.
- 실물 준비가 늦으면 서버·웹은 가상 장치로 검증하며 현장 의존 일정을 조정한다. D+28은 허가·설치·보정·출력과 개발/평가 분리를 확인한다.
- D+35에는 평가 분모·정답·성능 미달·실패와 통합 증거를 기록한다. D+42는 재시험과 제한도 함께 보고한다.

### F15 · 모의 구역과 이탈 관찰 영역

[Mermaid 원본](F15.mmd) · 이전 그림: v1.42 F15

상세 기준: [project/07](../spec/project/07.md) · [protocol/A1](../spec/protocol/A1.md) · [protocol/A4](../spec/protocol/A4.md) · [plan/09](../spec/plan/09.md)

- 이 도식은 관찰 대상과 데이터 관계를 나타낸다. 실제 위치·방향·거리·치수·설치 사진을 대신하지 않는다.
- 장소·카메라 모델·실제 시야·ROI·이탈 영역·배선·장치 인터페이스는 장소 선정과 실보드 점검·보정 후 결정한다.
- 같은 차량이 구역 밖으로 이동한 모습을 실제로 3초 연속 관찰해야 자동 종료한다. 미검출 3초를 이탈 증거로 바꾸지 않는다.
- 번호판 인식 없이 차량 관측과 동일성으로 사건을 관리한다. 동일성을 확인할 수 없으면 자동 종료 또는 이전 사건 결합을 추정하지 않는다.
- 실제 현장 사진과 보정 자료가 생기면 해당 파일과 촬영 조건을 추가한다. 현재 설계의 개념도를 실측 결과로 보고하지 않는다.

### F16 · 관측 실패, 실제 이탈과 관리자 예외

[Mermaid 원본](F16.mmd) · 이전 그림: v1.42 F16

상세 기준: [project/09](../spec/project/09.md) · [protocol/C5](../spec/protocol/C5.md) · [protocol/C6](../spec/protocol/C6.md) · [protocol/A3](../spec/protocol/A3.md) · [protocol/A4](../spec/protocol/A4.md) · [protocol/A5](../spec/protocol/A5.md)

- 사건 진행 중 대표 경로다. 전체 상태 전이표를 대체하지 않는다. 관측 실패 때 기존 사건과 사용한 안내 횟수는 유지한다.
- 품질이 정상 5초로 회복되더라도 동일성·중지·시각 등 나머지 조건이 충족되어야 새 후보를 시작한다. 동일성이 불명확한 경우를 단순 품질 회복으로 자동 해제하지 않는다.
- 미검출은 이탈 증거가 아니다. 이탈을 확인하지 못하면 사건을 유지하며 CLOSED_EXIT를 추정하지 않는다.
- 자동 사고 원인 판별은 범위에 없다. 관리자 예외의 종료 시각만으로 자동 재개하지 않는다.
- 현장 물리 중지는 원격으로 해제할 수 없다. 명시 재개 후에도 다른 중지가 남으면 안내를 재개하지 않는다. 세부 확인 토큰과 재개 절차는 C5·C6을 따른다.

### F17 · 과거 DB 복원은 상태 대조 후 운영자가 재개한다

[Mermaid 원본](F17.mmd) · 이전 그림: v1.42 F17

상세 기준: [storage/D6](../spec/storage/D6.md)

- 일반 프로세스 재시작과 과거 백업 DB 복원은 다르다. DB 복원에서는 사용 중이던 revision 범위를 다시 사용하지 않는다.
- 상태 대조 단계에서는 새 heartbeat·config/reported 및 보류한 durable 수신 기록을 수용한다. 일반 제어·외부 API/SSE·desired/commands 발행은 계속 차단한다.
- 옛 retained desired 또는 오래된 명령을 자동으로 재발행하지 않는다. recovery_hold는 서버 내부 운영 플래그이며 네트워크 enum을 추가하지 않는다.
- 서버 ACK를 받은 뒤 보드에서 삭제한 이력은 오래된 백업만으로 복구할 수 없다. 단일 호스트와 별도 사본의 동시 유실에서도 무손실·무중단을 보장하지 않는다.
- 최신 manifest를 확인할 수 없으면 최신 근거 복구 또는 별도의 승인된 설계 변경/재등록 절차 전까지 운영을 재개하지 않는다.

## 파일 사용과 개정

`.mmd`는 UTF-8 텍스트이며 Mermaid를 지원하는 환경에서 렌더링할 수 있다. 렌더링 없이 읽어도 노드·관계·순서·조건을 확인할 수 있다. PNG·SVG·PDF를 AI 입력의 필수 요소로 요구하지 않는다.

현장 위치와 시야 같은 공간 정보는 F15의 관계도만으로 확정하지 않는다. 실제 장소를 정한 후 현장 사진·치수·보정 조건을 추가하고 담당자가 검토한다.

이 폴더는 기존 설계를 설명한다. 기술 정책을 바꿀 때는 해당 상세 명세·계약·예제·시험을 먼저 함께 갱신하고, 영향을 받는 Mermaid와 사람용 그림도 맞춘다. 그림만 바꿔서 정책이 결정된 것으로 처리하지 않는다.

작성 기준: [C4 공식 설명](https://c4model.com/), [Mermaid 공식 소개](https://mermaid.js.org/intro/). 기존 v1.42에서 사용한 설계 모델과 표기를 유지했으며 새로운 아키텍처 구성요소를 추가하지 않았다.

## 검증 범위

`validation.json`은 Mermaid 문법 검사 결과다. 현재 환경에서 브라우저가 기동되지 않아 렌더 배치는 확인하지 못했다. 기존 Mermaid 번들의 문법 파서는 Node에서 실행했고, HTML이 없는 신뢰된 텍스트 라벨에 대해서만 DOM 정제 호출을 문자열 변환으로 대체했다. 문법 코드는 변경하지 않았으며 의도적으로 잘못 작성한 입력을 거부하는지도 확인했다. 이는 애플리케이션 구현이나 장치 성능 시험 결과가 아니다.
