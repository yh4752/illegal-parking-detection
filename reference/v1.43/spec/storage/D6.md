그림 F12. 사진 파일과 DB는 세 단계로 맞춘다

텍스트 도식: [F12](../../architecture/F12.mmd). 그림별 조건은 [아키텍처 안내](../../architecture/README.md)를 함께 확인한다.

서버는 업로드 의도를 DB에 예약하고, 잠금 밖에서 사진 파일을 저장한 뒤 DB의 완료 상태를 확정한다. 중간에 종료되면 파일 hash와 intent를 대조해 완료 또는 정리하며, 성공 응답 유실에 따른 같은 업로드 재시도는 200으로 처리한다.

· 사진과 DB가 모두 내구 저장된 뒤에만 201/200으로 응답한다.

· 만료 접근은 즉시 차단하며 재전송으로 보관기한을 연장하지 않는다.

그림 F17. 과거 DB 복원은 상태 대조 후 운영자가 재개한다

텍스트 도식: [F17](../../architecture/F17.mmd). 그림별 조건은 [아키텍처 안내](../../architecture/README.md)를 함께 확인한다.

과거 DB를 복원할 때는 외부 처리를 차단하고 최신 manifest 상한 이후의 새 revision 범위를 확보한다. 상태 대조용 수신만 먼저 연 뒤 장치와 서버의 정책·상태 차이를 확인하고 운영자가 재개한다.

· DB 복원으로 오래된 정책이나 명령을 장치에 다시 적용하지 않도록 한다.

· 최신 manifest를 입증할 수 없으면 운영을 재개하지 않는다.

| 상황 | 처리 기준 |
| --- | --- |
| 사진 저장 | DB 업로드 예약 → 잠금 밖 JPEG 내구 저장/rename → DB AVAILABLE 확정 → HTTP 201. 파일과 DB는 한 트랜잭션이 아님. |
| 업로드 중 종료 | intent와 파일 hash를 확인해 저장을 완료하거나 정리한다. HTTP 응답 유실 후 같은 내용을 다시 받으면 200을 반환하며 다른 내용은 충돌로 처리한다. AVAILABLE을 늦게 도착한 FAILED로 되돌리지 않는다. |
| 보관 만료 | 사진은 7일이 지나면 즉시 410으로 응답하고 파일은 24시간 안에 제거한다. 원문/리뷰/종료요약/명령은 기존 30일 기준을 따른다. 재전송으로 보관기한을 연장하지 않는다. |
| 오래된 재전송 | 최소 receipt·tombstone을 보존해 종료된 사건과 만료된 사진의 재생성을 막는다. 기존 키로 새 명령을 실행하지 않는다. |
| revision 복원 | DB 복원 경로 밖의 최신 manifest에 100만 번호 범위를 먼저 영속 예약한다. 복원 시에는 기존 상한 다음 범위를 사용한다. |
| 복원 인수 | API/SSE·발행 gate 중지 → 복원 → 새 범위 → 장치 상태/정책 대조 → 운영자 인수. 옛 outbox/desired 자동 재발행 금지. |

manifest 예약은 구역 처리 gate를 닫고 진행 중 쓰기를 마친 뒤 수행한다. 파일 I/O 중 DB 잠금을 잡지 않으며, 파일 예약 성공 전에 새 revision을 노출하지 않는다. 예약 뒤 DB 반영 전 종료는 번호를 건너뛰어 복구한다.

최신 manifest를 확인할 수 없으면 운영을 재개하지 않는다. 서버 ACK를 받은 뒤 보드에서 삭제한 이력은 오래된 백업만으로 복구할 수 없다. 단일 호스트 전체 유실 시에는 데이터 손실과 서비스 중단이 발생할 수 있다.

DB01~DB06에서는 동시 수신, ACK 유실, lease 역전, 사진 저장 단계별 종료, 보관 경계와 복원 gate를 시험한다. PostgreSQL 실행과 장애 주입 시험은 구현 후 수행한다. 현재 완료한 구문 점검과 실제 운영 시험은 구분한다.

근거: PostgreSQL Locking·Transaction Isolation·Constraints·Continuous Archiving, RFC8785. 원문 URL과 구체적인 처리 순서는 transactions.txt 끝에 수록했다. 구역 잠금·수치·manifest 방식은 프로젝트 선택이다.
