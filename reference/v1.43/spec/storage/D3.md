# D3 SDK 내부 저장과 현장 중단의 처리 순서

> v1.43 개발 AI 상세 명세 · v1.42 본문 이관 · 구현·실차 시험 전

원문: `08_연동과_저장_상세설계_v1.42.docx` / D3 SDK 내부 저장과 현장 중단의 처리 순서

문서 번호·이전 파일명은 [절별 위치 안내](../README.md)에서 찾는다. 표와 설명의 조건을 함께 적용한다.

그림 F10. 새 안내는 저장 후, 안전 중단은 즉시

텍스트 도식: [F10](../../architecture/F10.mmd). 그림별 조건은 [아키텍처 안내](../../architecture/README.md)를 함께 확인한다.

새 안내는 로컬 저장을 마친 뒤 현재 조건까지 재검사해 시작한다. 반면 안전 중단은 DB 지연이나 실패와 관계없이 우선 수행하며, 적용 성공 결과는 명령별 확인과 저장을 마친 뒤 전송한다.

· AI 제어 루프는 카메라 읽기·추론·JPEG 인코딩·fsync를 기다리며 멈추면 안 된다.

· stop_generation이 바뀌면 이전 안내 요청의 COMMITTED를 새 재생 허가로 사용하지 않는다.

AI 제어 루프가 판단 상태를 소유하고, SDK의 단일 SQLite writer가 상태와 발송 대기를 함께 저장한다. MQTT·사진 작업은 별도 worker다. 비동기 저장 완료를 기다리는 동안에도 AI의 이동·중지 처리가 계속되어야 한다. 카메라 읽기·추론·JPEG 인코딩도 제어 루프 밖에서 수행하도록 AI 어댑터의 인수 조건을 둔다.

| 항목 | 구현 기준 |
| --- | --- |
| 저장 요청 | operation_id, 예상 local_revision, 버전이 있는 checkpoint, 새 상태/시도/사진 작업 의도를 전달한다. 같은 요청을 재시도하면 원래 receipt를 반환한다. |
| 원자 저장 | checkpoint·횟수·message_id/device_seq·원본 메시지·outbox·명령 결과를 한 트랜잭션에 기록한다. 새 play는 COMMITTED를 확인한 뒤 실행한다. |
| 중단 예외 | 안전 stop/LED off는 DB 지연·실패와 관계없이 먼저 수행한다. APPLIED는 실제 회신을 받고 결과를 저장한 뒤 보고한다. |
| 늦은 저장 완료 | 중지 입력마다 내부 stop_generation을 증가시킨다. 이전 안내 요청의 COMMITTED가 늦게 도착해도 새 play를 실행하지 않는다. |
| 대기 한도 | 일반 명령 12개, 즉시 STOP 4개, 저장 대기 32개(긴급 4개 예약), 최신 heartbeat 1개로 제한한다. 한도를 넘으면 성공으로 처리하지 않고 장애·재전송 절차를 따른다. |
| 재시작 | 횟수와 사건을 보존하고 후보는 0으로 초기화하며 RESTART 보류를 적용한다. RECEIVED는 새 유효 재전송을 받은 뒤 guard를 다시 검사한다. EXECUTING 또는 실행 여부가 불명확한 명령은 재실행하지 않는다. 이전 boot 토큰은 무효다. |

필수 장애 순서는 ACK 유실, 명령 미접속, 시도 커밋 직후 종료, 저장 대기 중 STOP, 사진 큐 포화다. sdk_processing_v1.4.json에 입력·중간 상태·기대 결과를 정리했다. 실제 보드 언어·바인딩·저장 내구성과 출력 지연은 AI 환경 확인 및 BC06에서 검증한다.
